# Repository Guidelines: Backend Service (`test_backend`)

This repository contains the backend REST API service for the Project Tracker application. All agents, automation harnesses, and engineers must adhere to the conventions and guardrails defined below.

---

## 1. Tech Stack & Architecture

* **Framework**: FastAPI (v0.116+)
* **Database**: PostgreSQL 17 (production/staging) / SQLite `:memory:` (unit testing)
* **ORM**: SQLAlchemy 2.0 (`Session`, `select()`, `selectinload()`, Declarative Base)
* **Validation & Schemas**: Pydantic v2 (`BaseModel`, `ConfigDict(from_attributes=True)`)
* **Database Migrations**: Alembic
* **Linter & Formatter**: Ruff
* **Test Runner**: Pytest with FastAPI `TestClient`

---

## 3. Mandatory Coding Rules & Guardrails

### 3.1 Typing & Signatures
1. **Strict Type Annotations**: Every function, route handler, and helper MUST have full type annotations for all parameters and return types.
2. **Schema Separation**: 
   * Use `*Create` for POST payloads.
   * Use `*Update` for PATCH payloads (all fields optional with default `None`).
   * Use `*Read` for responses inheriting from `ORMModel` (`from_attributes=True`).
   * Never expose raw database model attributes directly without a Pydantic schema.

### 3.2 FastAPI Route Conventions
1. **Response Model**: Every endpoint MUST define `response_model` on the decorator (e.g. `@router.get("/projects", response_model=list[schemas.ProjectRead])`).
2. **Dependency Injection**: Always inject the database session using `db: DbSession` (type alias for `Annotated[Session, Depends(get_db)]`).
3. **Entity Retrieval**: Use the `get_or_404(db, Model, item_id)` helper function to look up entities. Do not manually craft repetitive `if not item: raise HTTPException(404)`.
4. **Transaction Integrity**: 
   * Use the `commit(db)` helper function to commit database transactions.
   * It catches `IntegrityError`, rolls back the session, and raises HTTP 409 Conflict.
5. **Eager Loading Relations**: When reading entities with relationships (e.g. `Task.labels`), eager-load them with `options(selectinload(...))` to prevent N+1 query overhead and detached instance errors.

### 3.3 Database Migrations
1. **No Direct Table Mutation**: Never alter database tables via raw SQL or scripts without an Alembic migration.
2. **Autogenerate Migrations**: When changing `app/models.py`, generate a new migration:
   ```bash
   alembic revision --autogenerate -m "describe_changes_here"
   ```
3. Inspect the generated migration in `alembic/versions/` to verify it accurately reflects the model change.

### 3.4 Logging & Code Hygiene
1. **No Raw Print Statements**: Never write `print(...)`. Use Python's standard logging:
   ```python
   import logging
   logger = logging.getLogger(__name__)
   ```
2. **No Raw SQL Strings**: Always use SQLAlchemy 2.0 query constructs (`select()`, `func`, `where()`). Never concatenate strings into SQL queries.

### 3.5 Test Integrity & Anti-Hallucination Rules
1. **Test Coverage Required**: Any new route, schema update, or bug fix MUST include corresponding test coverage in `tests/test_*.py`.
2. **Never Delete Assertions**: Under NO circumstances should existing assertions in `tests/` be deleted, commented out, or weakened to make tests pass.
3. **Isolated Test Execution**: Tests use the in-memory SQLite fixture from `tests/conftest.py`. Never add real database connections or network calls to unit tests.

## 4. Pre-Completion Verification Commands

Before completing any task or declaring work ready for pull request, execute the following commands and ensure zero errors:

```bash
# 1. Lint and style checks (must return exit code 0)
ruff check .

# 2. Automated test suite (must return exit code 0)
PYTHONPATH=. pytest tests/
```
